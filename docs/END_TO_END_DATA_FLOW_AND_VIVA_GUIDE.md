# InterviewIQ Studio — End-to-End Data Flow and Viva Guide

## 1. Purpose
This document describes the application data path, payload formats, model/API communication, local storage, and the meaning of common request/response fields. It separates implemented behaviour from optional integrations.

## 2. End-to-end workflow
1. **Candidate access:** Candidate creates a Candidate ID and six-digit PIN or signs in. The PIN is salted and hashed in Python. Candidate profile data is stored in browser localStorage.
2. **Interview setup:** Streamlit collects target role, experience, interview type, interviewer persona, question count and optional project context.
3. **Question selection:** Python builds the interview plan from the question bank. Dynamic technical question generation can call the configured model provider.
4. **Answer capture:** Typed answer arrives as UTF-8 text. Audio answer arrives as bytes plus MIME type (for example audio/webm).
5. **Transcription:** The speech module sends audio to a supported speech provider. Groq transcription uses multipart/form-data; Gemini audio transcription sends JSON containing base64-encoded audio data.
6. **Validation:** Python checks empty input and obvious random-character patterns. These rules are a conservative pre-check, not a complete semantic relevance classifier.
7. **Evaluation:** Python builds a prompt with question, answer, optional follow-up, candidate context and rubric. It sends an HTTPS request to the selected LLM provider.
8. **Response parsing:** Provider response is decoded from JSON. Python parses rubric values, clamps criterion scores to the supported range and computes a weighted overall score.
9. **Persistence:** Session dataclasses are converted to dictionaries and serialized with json.dumps. A browser component writes the JSON string into localStorage, keyed by candidate ID.
10. **History/progress:** History reads saved session records. Progress metrics and charts are derived in Python from those records; they are not themselves generated by an LLM.
11. **Report export:** Python generates Markdown, HTML and JSON reports from the saved session data.

## 3. Data formats by boundary

| Boundary | Format | Notes |
|---|---|---|
| Browser to Streamlit | Text/widget values, file bytes | Inputs and uploaded media |
| Streamlit to Python | Python strings, dicts, dataclasses, bytes | In-process; not an HTTP API call |
| Python to hosted LLM | HTTPS POST + JSON | Provider-specific request schema |
| Python to Groq transcription | multipart/form-data | Audio file + model field |
| Python to Gemini audio | JSON + base64 audio | MIME type and inline audio payload |
| Python to Ollama | Local HTTP + JSON | Requires Ollama running and reachable |
| Python to browser storage | JSON string | json.dumps / JSON.parse |
| Python to report download | Markdown / HTML / JSON | Export formats |

## 4. Example OpenAI-compatible request
~~~json
{
  "model": "provider-model-name",
  "messages": [
    {"role": "system", "content": "You are an interview evaluator. Return valid JSON."},
    {"role": "user", "content": "QUESTION: ...\nANSWER: ...\nRUBRIC: relevance, structure, evidence, clarity"}
  ],
  "temperature": 0.2,
  "response_format": {"type": "json_object"}
}
~~~
This is an illustrative OpenAI-compatible shape. Gemini uses contents, parts and generationConfig; Ollama's /api/chat endpoint has its own request schema.

## 5. Example evaluation response
~~~json
{
  "overall_score": 3.4,
  "rubric_scores": {
    "relevance": {"score": 4.0, "feedback": "Directly answers the distinction."},
    "structure": {"score": 3.0, "feedback": "Could use a clearer comparison."},
    "evidence": {"score": 2.5, "feedback": "No example was supplied."},
    "clarity": {"score": 4.0, "feedback": "Clear and concise."}
  },
  "key_strengths": ["Correctly identifies mutability."],
  "actionable_improvements": ["Add a code example and use case."],
  "stronger_answer_outline": "Define, compare, show syntax, explain use cases.",
  "suggested_followup_question": "When would you choose each type?"
}
~~~
The values are illustrative, not an actual model result.

## 6. Explain the important fields
- **model:** Provider-specific model identifier.
- **messages:** Array of conversational messages.
- **role:** Message source, usually system, user, or assistant.
- **content:** UTF-8 text content of a message.
- **temperature:** Sampling control; lower values usually reduce output variation, but do not guarantee correctness.
- **response_format:** Provider option requesting JSON output, where supported.
- **overall_score:** Aggregate practice score.
- **rubric_scores:** Per-criterion scores and feedback.
- **key_strengths:** Evidence-based positive observations.
- **actionable_improvements:** Specific suggestions.
- **stronger_answer_outline:** A structure for improving the candidate's authentic answer.
- **suggested_followup_question:** Next probing question.

## 7. What is an LLM token?
A token is a unit created by a model tokenizer. It may be a whole word, part of a word, punctuation or whitespace. A token is not the same thing as a JSON key, Python variable, API key or field. Exact token boundaries differ by model. Any token split shown in a presentation must be labelled illustrative unless generated by the exact model tokenizer.

For example, InterviewIQ evaluates answers. could be split into pieces similar to Interview, IQ, evaluates, answers, and punctuation. The actual split depends on the model tokenizer.

## 8. Login, history and progress storage
The current application uses browser localStorage for candidate profiles and session history. It is browser-specific and does not automatically sync between devices. The candidate PIN is stored as a salted hash, not plaintext. Live widget/application state is held in Streamlit session_state. API credentials belong in environment variables or Streamlit secrets, never localStorage or Git.

## 9. AI vs deterministic application logic
| Feature | Processing |
|---|---|
| Question generation | LLM/API or local Ollama if implemented/configured |
| Speech transcription | Hosted speech API in current speech module |
| Obvious gibberish pre-check | Python rules |
| Semantic evaluation | LLM |
| Score parsing and aggregation | Python |
| Login/PIN hashing | Python cryptographic functions |
| History/progress | Browser storage + Python calculations |
| Charts/reports | Streamlit/Python |

## 10. Important implementation caveats to disclose honestly
- A Python regex pre-check is not a complete semantic relevance detector.
- The current speech module supports Gemini/Groq transcription; Ollama itself does not provide speech transcription. Local speech requires a separate local ASR model such as faster-whisper.
- Do not describe browser-local Candidate ID/PIN as production-grade cloud authentication.
- Do not say every feature uses an LLM: authentication, persistence, chart calculations and report rendering are application logic.
- If provider errors trigger heuristic fallback, label that result clearly; never imply it came from a live LLM.
